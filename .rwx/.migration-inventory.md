# Migration Inventory

RWX ports of the GitHub Actions workflows into `.rwx/`, following gtm-sdk's
pilot pattern (`.rwx/` pipeline configs + this inventory). The pilot has been
flipped: `.rwx/ci.yml` and `.rwx/dagger-ref-drift.yml` are now the canonical
CI and drift checks, and their GHA counterparts were deleted. GHA remains
only for `pypi.yml` (PyPI publish — trusted publishing is GitHub-OIDC-bound)
and `pullfrog.yml` (vendor-managed agent harness); dependabot.yml stays to
bump the SHA-pinned actions in those two. Flip details are at the bottom of
this file.

## ci

Ported from `.github/workflows/ci.yml` (deleted in the flip) into
`.rwx/ci.yml`.

### ci: Jobs

- test (needs: [])
- lean-install (needs: [])
- schema-drift (needs: [], `if: github.event_name == 'schedule'`)

### ci: Secrets

- (none in the source workflow — it uses no secrets at all)
- Fork PRs therefore run the same full test suite as same-repo PRs — with no
  secrets to withhold, there is nothing to degrade (unlike gtm-sdk's
  `.rwx/tests-bazel.yml`, which skips fork PRs to keep vault tokens away from
  untrusted code).
- The source's `permissions: contents: read` block exists to shrink GHA's
  implicit `GITHUB_TOKEN`; RWX tasks receive no implicit token, so there is
  nothing to port. This repo is public, so even the `code` (git/clone) task
  needs no token — unlike gtm-sdk's `.rwx` configs, whose GITHUB_TOKEN vault
  secret exists only because that repo is private.

### ci: Environment Variables

- UV_LOCKED (source: workflow-level `env:`; port: task env on `deps` plus an
  `$RWX_ENV` export so every downstream `uv run` inherits it, reproducing the
  workflow-level scope)
- UV_PYTHON ("3.13"; source: astral-sh/setup-uv's `python-version` input,
  which sets UV_PYTHON; port: task env on `deps`/`lean-install` plus the same
  `$RWX_ENV` export from `deps`)

### ci: Notable Steps

- actions/checkout (default fetch-depth: 1) → git/clone 2.2.0 with its
  default shallow fetch; nothing in the test suite or the two `--check`
  scripts reads git history. Pinned to 2.2.0, the current catalog version at
  port time (gtm-sdk's configs pin 2.1.0 from a month earlier; same major).
- astral-sh/setup-uv (python-version: "3.13", latest uv) → manual
  checksum-pinned astral.sh installer at uv 0.11.29. No packaged
  `uv/install` leaf exists (verified via `rwx packages list` 2026-10-03 —
  `python/install` installs Python, not uv), same gap gtm-sdk's configs
  document. The source pinned only the action, not the uv version; the port
  pins uv explicitly (validated locally: `UV_LOCKED=1 UV_PYTHON=3.13 uv sync`
  + full pytest suite green on 0.11.29) because an unpinned `curl | sh`
  installer can't reproduce setup-uv's action-SHA pinning any other way.
- `uv sync` → `deps` task (no `filter:` — gtm-linear installs itself
  editable and tests import scripts/ and operations/).
- Tests / Operations are current / Generated code is current → `test` task,
  same three commands in the same order.
- Build + lean-venv import check → `lean-install` task, `use:`ing
  `[uv-install]` (not `[deps]`) to mirror the source job, which never runs
  `uv sync`. The strawberry-leak guard captures the pip listing before
  grepping it: the source's `grep -q` at the end of a pipe can take SIGPIPE
  under `set -o pipefail` (141) and make the `if` false — failing open
  exactly when the leak exists.
- `uv run pytest -q -m network` → `schema-drift` task, gated on
  `init.event-type == 'schedule'` and `cache: false` (see below).

### ci: Triggers

- pull_request with no branches filter → github.pull_request trigger with no
  `if:` (deliberately unfiltered, matching the source's `pull_request: {}`).
- push `branches: [main]` → github.push trigger with
  `if: ${{ event.git.branch == 'main' }}`.
- schedule `17 6 * * 1` (weekly Monday 06:17 UTC) → cron trigger keyed
  `weekly-schema-drift`. One caveat vs GHA: a single RWX pipeline mixes all
  three trigger types, so on cron runs the `test` and `lean-install` tasks
  run too — identical to the source, where the schedule event runs the whole
  workflow with only schema-drift additionally gated on the event name.
- cli trigger added (no source equivalent — the workflow has no
  workflow_dispatch) for manual `rwx run` validation; mirrors the push
  trigger's init.

### ci: Caching decisions

- `test`, `lean-install`, `deps`, `uv-install`: default content-based
  caching is correct — all are deterministic functions of the repo files
  (tests are respx-mocked, no network). The source workflow had no
  actions/cache, so this is a strict improvement, not a regression.
- `schema-drift`: `cache: false` — the result depends on Linear's live
  upstream schema, not just this repo's files; a cache hit would freeze the
  drift check exactly when upstream moved.

### ci: TODOs / Gaps

- uv is installed via a manual installer script (no packaged leaf yet); the
  version is pinned and checksum-verified, but bumping it is now a manual
  step owned by this file. Re-validate `uv sync --locked` + the pytest suite
  whenever it moves.
- workflow_dispatch is not ported (none existed in the source); the added
  `cli` trigger covers manual dispatch.

## dagger-ref-drift

Ported from `.github/workflows/dagger-ref-drift.yml` (deleted in the flip)
into `.rwx/dagger-ref-drift.yml`.

### dagger-ref-drift: Jobs

- check (needs: [])

### dagger-ref-drift: Secrets

- `GITHUB_TOKEN` (custom vault `sdk-python-linear`, locked) — the source
  workflow used GHA's implicit `github.token` with
  `permissions: issues: write`; RWX has no implicit token, and the
  `${{ github.token }}` App expression was probed live (2026-10-03, run on
  the throwaway probe PR) and is **not available in task env**, so a PAT is
  required. The vault's access grants: repository runs on `main` (the
  weekly cron's ref) and the account user (cli dispatches). A bare `*`
  branch pattern was granted, tested, and revoked — glob `*` does not cross
  `/`, so it never matched this repo's `conductor/*` branch names; `main`
  is granted explicitly instead. Fork-PR runs never match the repository
  grant (different repository slug). The PAT must be fine-grained with
  Issues: Read/Write on exactly elviskahoro/sdk-python-linear. Provision
  with `rwx vaults secrets set --vault sdk-python-linear GITHUB_TOKEN=<pat>`;
  the pipeline reads it as
  `${{ vaults.sdk-python-linear.secrets.GITHUB_TOKEN }}`. Until the secret
  lands, the `check` task fails fast with a named message (vault access
  denied → "The vault is locked"; access granted but secret missing → "The
  secret GITHUB_TOKEN was not found"). (History: before the swap, the
  pipeline referenced the default vault's `GITHUB_TOKEN`, a broad classic
  PAT probed live — authenticates, issues:read works, ADMIN — that is
  shared with gtm-sdk's pipelines and so could not be narrowed in place.)
- The version-pin check and `git ls-remote` need no auth: the target repo
  (elviskahoro/sdk-python-publish-to-pypi) and this repo are both public.
  Upstream protects `v*` release tags from update and deletion with a GitHub
  ruleset with no bypass actors. The SDK repo also records the expected commit
  SHA beside the Dagger pin; the weekly drift check and the PyPI workflow
  verify the tag still resolves to that SHA before running the module.

### dagger-ref-drift: Environment Variables

- GH_TOKEN (source: `github.token` implicit; port: vault secret, with
  `cache-key: excluded` so the token value can never pin the task's cache
  key)

### dagger-ref-drift: Notable Steps

- actions/checkout → git/clone 2.2.0, shallow (the check reads the current
  workflow and `scripts/dagger_ref_drift.sh`, never history).
- gh CLI → `github/install-cli 1.1.0` packaged leaf with `cache: false`
  (the package installs *latest* gh and sets no TTL; caching it indefinitely
  would freeze whatever version the first run got — the exact hazard RWX's
  caching docs describe. `cache: ttl` is command-task-only, so the port
  opts out entirely; at weekly cadence the reinstall is negligible).
- `scripts/dagger_ref_drift.sh` validates the single stable
  `vMAJOR.MINOR.PATCH` pin, confirms that the tag exists upstream and still
  resolves to its recorded commit SHA. The PyPI workflow performs the same
  verification immediately before the Dagger build. The drift task compares
  stable tags semantically, ignoring prereleases; a missing
  pinned tag or failed upstream lookup fails clearly rather than silently
  skipping the check or recommending a downgrade. It opens or refreshes the
  exact-title stale-ref issue only when a newer release exists, refreshes its
  marked automation issue when the latest release changes, and closes only
  that marked issue with a recovery comment when the pin catches up. `gh issue
  list` / `gh issue view` / `gh issue create` / `gh issue edit` / `gh issue close` pass
  `-R elviskahoro/sdk-python-linear` explicitly (the source relied on gh
  inferring the repo from the checkout's git remote, but git/clone strips
  the `.git` directory by default, so there is no remote to infer from); a
  GH_TOKEN preflight runs before the drift task's upstream lookup and fails
  with a named cause when the vault secret is missing; publish-time
  `--verify-tag` mode does not need GitHub issue access.
- `check` task is `cache: false` — the result depends on the upstream
  repo's release tags and on which GitHub issues are open, neither of which
  is part of this repo's file contents.

### dagger-ref-drift: Triggers

- schedule `0 9 * * 1` (weekly Monday 09:00 UTC) → cron trigger keyed
  `weekly-dagger-ref-drift`, matching the source schedule. During the pilot
  it was staggered to 10:00 so the two check-then-create pipelines could not
  both see `open=0` and file duplicate stale-ref issues while running side
  by side; with the GHA workflow deleted in the flip, the stagger is moot
  and the source's 09:00 is restored.
- workflow_dispatch (no inputs) → `cli` trigger for manual `rwx run`
  validation, plus a `dispatch` trigger keyed `dagger-ref-drift` for ad-hoc
  checks from the Cloud UI / API / CLI. A dispatch with `--ref main`
  populates `event.git` from main and unlocks vaults exactly as the weekly
  cron does, so `rwx dispatch dagger-ref-drift --ref main` is the
  empirical test for the cron path's vault access.

## Out of scope (deliberately not ported)

### pypi.yml (publish)

Not ported. The build half would port fine (dagger CLI install +
`dagger -m ...@v0.2.2 call build`, with `use:`-chaining replacing the
artifact upload/download between the build and publish jobs). The publish
half does not: it publishes via pypa/gh-action-pypi-publish with
`id-token: write` — PyPI trusted publishing, which is bound to GitHub's OIDC
identity and has no RWX equivalent. An RWX port would need a long-lived
PyPI API token in the vault, losing the no-credential property, and would
also lose the `environment: pypi` protection gate (GHA environments have no
RWX analog). gtm-sdk's RWX pilot likewise left its release workflow in GHA.
Revisit only if PyPI grows trusted-publisher support beyond
GitHub/GitLab CI.

### pullfrog.yml

Not ported. It is a vendor-managed agent-dispatch harness
("PULLFROG ACTION — DO NOT EDIT EXCEPT WHERE INDICATED"), not CI: a
workflow_dispatch prompt input, OIDC (`id-token: write`) for pullfrog's own
auth, and a spread of provider API keys. It has no build/test semantics to
migrate, and gtm-sdk's RWX pilot kept its identical pullfrog.yml in GHA too.

### dependabot.yml

Not a workflow — it bumps the SHA-pinned `uses:` refs in
`.github/workflows/`. Post-flip it keeps covering the GHA that remains:
`pypi.yml` (checkout, dagger-for-github, upload/download-artifact,
gh-action-pypi-publish) and `pullfrog.yml`. Nothing to trim — the config is
directory-wide and both remaining workflows use SHA-pinned actions. The
dagger module ref inside pypi.yml's `run:` step stays invisible to
Dependabot and is checked weekly by `.rwx/dagger-ref-drift.yml`.

## Pin maintenance (hand-maintained pins in these configs)

Dependabot only bumps the SHA-pinned `uses:` refs in `.github/workflows/`;
nothing automated covers these. Revisit on any bump:

- Local rwx CLI — 3.33.0+ required to manage these configs (`vaults list` /
  `vaults update` / `vaults access` don't exist in 3.25, which this
  machine had when the vault work started). Installed as a standalone
  vendor binary at `~/.local/bin/rwx` (no brew/mise/asdf on this machine);
  upgrade by downloading the `rwx-darwin-aarch64` asset from
  https://github.com/rwx-cloud/cli/releases and replacing the binary.
- uv version + installer sha256 — `.rwx/ci.yml` `uv-install` (keep the two
  in lockstep; re-validate `uv sync --locked` + the pytest suite on bump).
- `rwx/base 1.2.0` — both files (base image config).
- `git/clone 2.2.0` — both files (clone leaf).
- `github/install-cli 1.1.0` — `.rwx/dagger-ref-drift.yml` (gh leaf; the
  version it installs is latest-by-design, only the leaf ref is pinned).
